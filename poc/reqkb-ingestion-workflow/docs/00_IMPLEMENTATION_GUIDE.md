# ReqKB ingestion implementation guide

## Purpose

This document turns the approved RD → ReqKB workflow into an implementation plan. The implementation prepares evidence-backed requirement units only. It must not infer API, Screen, DatabaseTable, Batch or other BD artifacts.

## Target workflow

```text
RD Markdown folder
→ document registry
→ deterministic Markdown parser
→ SourceUnit builder
→ parser metadata
→ rule-based validator
→ repair/review queue
→ terminology canonicalizer
→ lightweight ontology tagger
→ evidence/schema validator
→ ReqKB persistence
→ keyword/vector-ready output
```

## Components

| Component | Responsibility | Must not do |
|---|---|---|
| `DocumentRegistry` | Discover files, assign document IDs, hashes and versions | Interpret business meaning |
| `MarkdownParser` | Produce deterministic structural blocks and line ranges | Summarize or rewrite text |
| `SourceUnitBuilder` | Group blocks into stable meaningful evidence units | Add ontology meaning |
| `SourceUnitValidator` | PASS/SPLIT/MERGE/REVIEW/REJECT | Invent repaired text |
| `TerminologyCanonicalizer` | Link aliases to canonical business terms | Replace raw source text |
| `OntologyTagger` | Attach lightweight requirement annotations | Infer design artifacts |
| `EvidenceValidator` | Verify annotations are supported by raw text | Accept unsupported LLM output |
| `ReqKBRepository` | Persist documents, units, annotations and lineage | Act as the parser or tagger |
| `IngestionPipeline` | Orchestrate stages, retries and queues | Hide stage failures |

## Recommended libraries

- Python 3.12.
- `markdown-it-py` for deterministic Markdown tokenization.
- `pydantic>=2` for data contracts and structured-output validation.
- `sqlalchemy>=2` and PostgreSQL for persistence.
- PostgreSQL full-text search initially; `pgvector` only when semantic retrieval is added.
- `typer` for a small ingestion CLI.
- `pytest`, `pytest-cov`, and `hypothesis` for tests.
- An LLM provider with native JSON Schema output, or LangChain `with_structured_output`, only in `OntologyTagger`.

## Delivery sequence

### Milestone 1 — deterministic foundation

Implement registry, parser, SourceUnit builder, stable IDs, JSONL export and unit tests. No LLM.

Exit criteria:

- same unchanged input produces identical SourceUnit IDs;
- every unit traces to document and exact line range;
- raw text is byte-equivalent to the source slice after newline normalization policy;
- parser failures are explicit.

### Milestone 2 — validation and repair queues

Implement validator rules, statuses and repair lineage. Repair may regroup source blocks but must not rewrite the source.

Exit criteria:

- every unit has a deterministic status;
- SPLIT/MERGE decisions create parent/child lineage;
- REVIEW records include rule hits and source context;
- REJECT is reserved for unusable input, not difficult semantics.

### Milestone 3 — lightweight semantic annotation

Implement terminology canonicalization, ontology schema, rule annotations and LLM fallback.

Exit criteria:

- ontology output conforms to schema;
- design concepts are prohibited;
- low-confidence or unsupported annotations enter review;
- raw text remains unchanged.

### Milestone 4 — persistence and incremental ingestion

Implement PostgreSQL persistence, add/update/remove handling, stale records and metrics.

Exit criteria:

- unchanged files are skipped;
- changed files replace only assertions derived from changed units;
- removed units are marked inactive or deleted according to retention policy;
- reruns are idempotent.

## Cross-cutting rules

1. Raw evidence is immutable.
2. IDs are deterministic and never generated by an LLM.
3. Every annotation references exactly one or more SourceUnit IDs.
4. Every pipeline output records component and schema versions.
5. LLM output is untrusted until Pydantic and evidence validation pass.
6. No unit may become `ACTIVE` in ReqKB when validation or evidence checks fail.
7. Human corrections must be stored separately from raw source and model output.

## Definition of done

The implementation is complete for the POC when a selected folder of Markdown RD files can be ingested repeatedly into PostgreSQL with stable SourceUnits, deterministic metadata, validation decisions, lightweight ontology annotations, review queues and incremental update behavior, while preserving exact source provenance.
