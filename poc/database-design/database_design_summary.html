Database architecture at a glance

Standalone summary cho coding agent và reviewer: dữ liệu đi đâu, table nào giữ truth, rerun/baseline/publication hoạt động thế nào, và boundary nào phải giữ khi POC scale lên main.

1. Mental model ngắn nhất

SYSTEM OF RECORD Object Store Immutable payload bytes / structured artifacts
  • raw source
  • normalized document
  • parsed/chunk/enrichment bundle
  • publication manifest
SYSTEM OF RECORD Catalog DB Business identity + lineage + governance
  • SourceRevision / StageExecution
  • OutputSlot / OutputSet registry
  • BaselineSelection / BaselineHead
  • Publication / PublicationHead
PUBLISHED STATE Neo4j / ReqKB Semantic knowledge đã publish
  • Requirement / Function nodes
  • semantic edges
  • published ontology classification
Rule: một logical state chỉ có một canonical owner. Runtime checkpoint, MLflow trace hoặc relational projection không được tự trở thành business truth.

4. Rerun và baseline — phần dễ implement sai nhất

Rerun

SLOT-CHUNK-REV001 ├── OUTSET-A ← run 1 ├── OUTSET-B ← run 2 └── OUTSET-C ← run 3

Rerun cùng workspace + artifact_role + scope_fingerprint phải reuse cùng OutputSlot; chỉ tạo OutputSet candidate mới.

Baseline

latest OutputSet ≠ current baseline BaselineSelection = append-only history BaselineHead = current pointer + lock_version

Baseline update dùng optimistic concurrency. Không dùng MAX(created_at), newest run hoặc latest file để suy ra current truth.

5. Exact lineage và stale detection

StageInput phải pin exact version

StageInput ├── output_set_id ├── source_baseline_selection_id └── resolved_hash

Execution history không rewrite khi baseline đổi.

Stale là derived state

input baseline used == current BaselineHead → CURRENT input baseline used != current BaselineHead → STALE

POC derive on demand; main có thể thêm rebuildable staleness projection nếu query cost tăng.

8. Runtime / observability boundary

RUNTIME

LangGraph now

checkpoint, interrupt/resume, retry, execution mechanics.
Not owner of: baseline, publication, business lineage.
OPTION

Prefect later

switch khi scheduler/worker/backfill/data-heavy workload trở thành requirement chính.
Boundary: same minimal WorkflowRuntimePort.
OBSERVABILITY

MLflow later

trace, evaluation, experiment comparison.
Not SoR: business provenance tối thiểu vẫn ở Catalog DB.
runtime_ref examples: langgraph:<opaque-id> prefect:<opaque-id>

10. ADR decisions đã khóa

ADR-001

Publication scope theo stable SourceAsset

Lý do: OutputSlot scope theo SourceRevision; nếu publication cũng scope theo OutputSlot, revision cũ và mới có thể cùng “active”.
Decision: PublicationScope = KnowledgeSpace + SourceAsset + publication_role.
ADR-002

StageInput dùng dual FK + XOR CHECK

Lý do: POC chỉ có SourceRevision và OutputSet; ưu tiên real referential integrity hơn generic type + id.
Trade-off: thêm durable input type mới có thể cần migration.
ADR-003

Minimal WorkflowRuntimePort

Lý do: dùng LangGraph nhanh nhưng không lock Web App/database vào framework.
Decision: expose start/resume/cancel/status; framework-specific semantics ở adapter.

12. Acceptance scenario cho coding agent

1. Upload Requirement.xlsx → SOURCE-001 / REV-001 2. Start workflow → RUN-001 3. Parse lần 1 → OUTSET-A trong SLOT-CHUNK-REV001 4. Parse lại → OUTSET-B trong cùng OutputSlot 5. User chọn OUTSET-B → BASELINE-002 → BaselineHead 6. Next stage pin OUTSET-B + BASELINE-002 → OUTSET-C 7. User đổi baseline về OUTSET-A → BASELINE-003 8. OUTSET-C vẫn tồn tại nhưng được detect STALE 9. Publish accepted output → PUB-001 ACTIVE 10. Upload REV-002, publish → PUB-002 ACTIVE, PUB-001 SUPERSEDED

Nếu repository/schema không support được scenario này thì implementation chưa đạt architecture baseline.
