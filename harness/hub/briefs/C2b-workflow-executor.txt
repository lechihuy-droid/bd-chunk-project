CRITICAL GATE SEMANTICS (do not implement the naive reading of the BD prose):
runtime_pipeline's `act()` node checks `_needs_interrupt` as the FIRST thing
it does, BEFORE producing any output. If a gate is pending, it returns
`goto="act"` (itself) with an interrupt tied to `node="act"`, and produces NO
output that call. On resume, `resume_run_stream` sets `start_node =
metadata.next_node` (which `create_interrupt` set to the SAME node) and calls
`execute_run(run_id, start_node=start_node)` — i.e. resume RE-ENTERS the same
node, which now sees a resolved interrupt via `_has_resolved_interrupt` and
proceeds to do its real work and advance. Mirror this exactly for
`gate: approval` nodes: check gate-resolved BEFORE calling the provider; if
not resolved, create the interrupt (node=<this node's id>), emit interrupt +
state_snapshot events, and STOP the generator without advancing your node
pointer past this node. Your own resume function must re-enter this SAME
node id/index (not "the next node" — the BD prose's "resume continues from
next node" is imprecise; implement the self-loop pattern above, which is what
the existing runtime actually does and what C3's HITL gate panel will expect).

ROUTE CONTRACT GAP (real, not hypothetical): the existing
`POST /api/agent/runs/{run_id}/interrupts/{interrupt_id}/resume` route in
server.py is hardcoded to `runtime_pipeline.resume_run_stream`, which resumes
into `runtime_pipeline.NODES` (prepare_context/plan/act/review/finalize).
Workflow runs are NOT pipeline runs and must NOT be resumed through that
route — reusing it would silently execute the pipeline's deterministic
`plan`/`act` node functions instead of your workflow's real nodes (the C2a
sample workflow even reuses the node ids "plan"/"act", making the collision
concrete, not just theoretical). You MUST add your own resume route for
workflow runs (see TASK 3). The BD's "GET reuse existing /api/agent/runs
endpoints, no new read endpoints" instruction is still correct and unaffected
— `GET /api/agent/runs/{run_id}` and `.../events` are generic state/event
readers that work for any run regardless of which executor produced it; only
the POST resume path needs a workflow-specific route.
