CONTRACT NOTES (resolve these against the ACTUAL workflow_exec.py before
coding, since C2b lands first — do not guess):
- Routes (per C2b brief): `POST /api/workflows/{workflow_id}/runs` body
  `{"objective": str}`, response is an SSE stream (`text/event-stream`), NOT a
  JSON body — do not `await response.json()` on it, start the fetch+reader
  loop immediately and navigate to the run view as soon as the first event
  (or the initial `state_snapshot`) gives you the `run_id`. If no event
  reliably carries `run_id` before you need to navigate, read it from
  `GET /api/agent/runs` (poll or diff) or from the `state_snapshot` event's
  `state.run_id` field — check `runtime_state.create_run`'s return shape in
  services/runtime_state.py if unsure what the run dict contains.
- On 404 (unknown workflow_id) or 400 (`{"errors": [...]}` validation
  failure) from the runs POST: show the error inline on the #/workflows list
  page (toast/inline text near the Run button), do not navigate.
- Resume route: `POST /api/workflows/runs/{run_id}/interrupts/{interrupt_id}/
  resume` — DISTINCT path from the existing pipeline's
  `/api/agent/runs/{run_id}/interrupts/{interrupt_id}/resume` (do not call the
  pipeline route for workflow runs — see C2b brief's "ROUTE CONTRACT GAP").
  Body shape: mirror `runtime_pipeline.resume_run_stream`'s convention —
  `{"action": "resume"|"reject", "payload": {...edited fields...}}` — but
  VERIFY this against the landed `resume_workflow_run_stream(run_id,
  interrupt_id, payload)` signature/body in workflow_exec.py before wiring it
  up; if it destructures differently, follow the code, not this note.
- KNOWN GAP — Reject is not a hard stop: `runtime_interrupts.resolve_interrupt`
  records whatever `action` string you send (default "resume") but neither
  `runtime_pipeline.resume_run_stream` nor (per the C2b brief's design)
  `resume_workflow_run_stream` branches on it — both simply mark the
  interrupt resolved and re-enter the SAME node, which then proceeds to call
  the provider regardless of action value. This means clicking "Reject" as
  specified cannot currently skip/abort the gated node — it can only be
  recorded for audit. Implement it honestly: send `action: "reject"` when the
  user clicks Reject (so it's in the interrupt/event log), but do NOT word
  the button or any status text as "node skipped" or "run stopped" — the run
  will still execute that node's provider call. If you want to soften this,
  you may show a confirm dialog on Reject ("this will still run the node —
  continue?") before calling resume. Do not attempt to add real
  reject-aborts-node logic yourself — that would require a workflow_exec.py
  change, out of C3's scope whitelist.
- Interrupt event payload shape (per C2b brief step 1.b): `{"node": <id>,
  "prompt": <rendered prompt text>, "objective": <str>}` inside the
  `interrupt` event's `payload` field (top-level event fields also include
  `interrupt_id`, `reason`, `node`). Show `payload.prompt` in the gate panel
  so the user can see exactly what will be sent to the provider before
  approving — this is the HITL review surface, do not just show a bare
  "approve?" with no content.
- Event types you will see on the run stream (all via `to_sse`, `event: <type>
  \ndata: {...}`): `assistant_delta` ({node, text} plus message_id — append
  `text` to that node's streaming output area), `node_update` ({node, goto} —
  `goto: null` means that was the last node), `state_snapshot` ({state} — the
  full run state dict, use it to redraw the node timeline/badges and the
  budget bar after every event since it's the cheapest source of truth),
  `interrupt` ({interrupt_id, reason, node, payload} — show the HITL gate
  panel, stop appending to the timeline until resolved), `done` ({state} or
  final usage — run finished, stop the stream reader), `error` ({message} —
  show inline, stop the stream reader). Treat unknown event types as no-ops
  (forward-compatible), do not throw.
- Read/backfill endpoints (reuse as-is, no new backend routes): `GET
  /api/agent/runs/{run_id}` (generic run state reader — works for workflow
  runs too since C2b uses the same `runtime_state`/`runtime_events` storage)
  and `GET /api/agent/runs/{run_id}/events` (full event history — use this to
  reconstruct the run view if the user navigates directly to
  `#/workflows/runs/{run_id}` via URL/refresh instead of arriving from a live
  stream: replay the events list once through the same event-handling
  function you use for live SSE, then only open a live stream if the run's
  `status` is still "running").
