TWO CONTRACT FACTS THAT CHANGE THE SHAPE OF THIS WORK — verify them yourself
by reading runtime_children.py before assuming the BD prose is complete:

1. `create_child_run` is a pure bookkeeping call — it creates the child's run
   record (+ optionally a gitjob) and returns immediately. It does NOT execute
   any agent, call any provider, or produce any output by itself. "Child
   executes via same node-execution helper" (per BD) means workflow_exec
   itself must drive the child's provider call inline, synchronously, using
   the same render/call/collect logic C2b built for regular nodes — then
   call `runtime_children.complete_child_run(child_run_id, artifacts)` or
   `fail_child_run(child_run_id, message)` yourself once the child's provider
   stream finishes. There is no background executor to hand this off to.
2. `create_child_run` raises `ValueError("Only the lead runtime can spawn
   child runs")` unless the PARENT run's `metadata.agent_id == "lead"`. C2b's
   brief already mandates the workflow run be created with `agent_id="lead"`
   for exactly this reason — verify C2b actually did this (check the run's
   metadata in a quick sanity test) before writing your own tests, otherwise
   every spawn will hard-fail with a confusing ValueError that looks like a
   governance bug but isn't.
3. `_packet()`'s accepted raw_packet keys are exactly: objective, agent_id (or
   agent), allowed_paths, allowed_tools, skills, budget (dict, passed through
   as-is, NOT validated against any schema), timeout_seconds, use_gitjob.
   `budget` already flows through untouched — you very likely do NOT need to
   add a field to runtime_children.py at all; just pass `agent["budget"]`
   (the spawned agent's own profile budget dict, per BD: "budget from agent
   profile") as `raw_packet["budget"]`. There is no `handoff_contract` field
   in `_packet()` and adding one is unnecessary — the "write findings to
   blackboard claims.jsonl" contract can be enforced entirely inside
   workflow_exec's own child-execution code (you already control both ends:
   you build the child's raw_packet AND you drive its execution loop AND you
   decide where its output gets written). Only touch runtime_children.py if,
   after reading it, you find an actual gap — do not add speculative fields.
4. `allowed_paths`/`allowed_tools` subset-of-parent enforcement in
   `_ensure_subset` is a no-op whenever the PARENT's `metadata.allowed_paths`/
   `allowed_tools` is empty (the check returns early if `not parent`). The
   workflow schema has no allowed_paths/allowed_tools concept, so unless you
   deliberately set them on the workflow run, this check is permissive by
   default — that's fine and expected, just don't be surprised when a
   deliberately-too-broad child packet in a test doesn't raise.
